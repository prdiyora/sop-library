11.4.C 2. What Vercel does

  • Hosts static HTML/CSS/JS.
  • Connects to GitHub and deploys on push.
  • Non-production branches get Preview deployments.
  • Configured production branch deploys to production.
  • api/*.js files become server-side Node.js Functions.
  • Environment Variables store secrets server-side.

Important: Current 05:30 GSC collection is done by existing scheduled automation, not Vercel Cron. A Vercel Cron hitting /api/gsc-health only checks data; it does not fetch GSC or update GitHub.

11.4.E 4. GitHub token → Vercel Environment Variable

The API reads private GitHub main/data.json, so Vercel needs a server-side GITHUB_TOKEN.

  1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens.
  2. Resource owner: client-a-store.
  3. Repository access: only gsc.
  4. Permissions: Contents Read-only; Metadata Read-only/default.
  5. Generate token; copy it only into Vercel. Never paste into chat, docs, source, HTML, screenshots, or logs.
  6. Vercel → project (vercel project) → Settings → Environment Variables.
  7. Name GITHUB_TOKEN; value = token; target = Preview (and branch restriction migration/vercel if using branch-specific preview env).
  8. Save and redeploy latest Preview deployment. Environment changes do not alter already-built deployments automatically.
  9. Test /api/gsc-health; expected ok:true, 13 expected/checked projects, allProjectsValid true.

Token must never be returned to browser. Rotate it if exposed or expired.

11.4.I 8. data.json schema

Root keys: updatedAt, projects. Each project has name, siteUrl, daily. Daily fields: date, clicks, impressions, ctr, position. CTR stored as decimal ratio (0.01 = 1%).

11.4.K 10. Daily 05:30 scheduler workflow

  1. 05:30 Asia/Kolkata trigger.
  2. Query 13 GSC properties.
  3. Normalize daily date rows and metrics.
  4. Merge with old history by date key; no duplicate rows; preserve old rows.
  5. Commit data.json to GitHub main.
  6. Read back main/data.json; validate JSON and project count.
  7. Call Vercel Preview health endpoint.
  8. Smoke-test /api/gsc and dashboard.

GSC reporting can be delayed. Do not fill missing dates with zero. Next scheduled run should backfill/merge when data becomes available. Existing scheduler ID: (scheduler ID). Do not create duplicate schedules unless replacing the current workflow with an approved tested migration.

11.4.L 11. Vercel Cron – optional, not current data-fetch system

Vercel Cron sends an HTTP request to a deployed route. It does not magically connect GSC or write GitHub. If a cron calls /api/gsc-health, it only checks the snapshot. Full GSC ETL requires OAuth/service-account auth, API query code, merge/write logic, retries, idempotency/locking, and monitoring. Keep current working scheduler until replacement is tested end-to-end.

11.4.P 15. Security

  • No secrets in code/docs/chat/screenshots.
  • GitHub fine-grained token limited to selected repo + Contents Read-only.
  • Secrets stored in Vercel Environment Variables.
  • No token returned to browser or error response.

  • Restrict private repo and Vercel team access.
  • Do not deploy unreviewed code with production secrets.

11.4.Q 16. GSC metrics vs business goals

  • Clicks, impressions, CTR, position → GSC.
  • Organic Search sessions/users and engagement → GA4.
  • Purchases/revenue → Shopify + GA4 purchase event.
  • Leads/forms/calls → GA4 event + CRM/call/form tracking.
  • CTR = clicks ÷ impressions × 100.
  • Use GSC period-level average position; don't average daily average positions manually.
  • Example goal: 700 clicks baseline, 770 target (+10%); actual/target × 100 = achievement. Targets are team-defined.

11.4.S 18. Minimum-deployment strategy – reusable across all projects

Goal: reliable dashboard with minimum unnecessary Vercel deployments, GitHub API reads/writes, GSC queries, automation runs and AI/token usage.

18.1 Recommended architecture: deploy code rarely, update data separately

LayerMinimum strategyWhy it saves usage

18.2 Deployment decision rule

  • Data-only change (new rows in data.json): do not redeploy Vercel. The API reads the latest GitHub main snapshot when requested.
  • Dashboard/API code change: push one reviewed commit to migration/vercel; Git integration creates one Preview deployment.
  • Preview passes and release approved: follow the production release process. Do not deploy for each daily data refresh.
  • More properties in same dashboard: add a site config entry; do not clone the entire dashboard/API for every site.
  • Different client/team with separate secrets, access rules, billing or branding: use a separate project/repo when isolation is needed.
  • Batch related code/config edits and deploy once; environment-variable changes also require a new deployment to take effect.

18.3 Keep GitHub, GSC and API usage low

  1. GSC: one Search Analytics query per property per daily run for the required date window; use only required dimensions (date) and metrics. Do not repeat identical queries in the same run.
  2. Backfill: query only missing/recent dates or a deliberate bounded lookback; merge by date key idempotently.
  3. GitHub: prepare the merged JSON in memory and commit once after all properties are processed; avoid one commit per site/date.
  4. Scheduler GitHub reads: read source once before merge and read back once after commit for validation.
  5. Dashboard: fetch only the selected site and selected date range; do not fetch all 13 sites on every page view unless portfolio totals require it.
  6. Health: run once after commit; no polling every few seconds.
  7. No-op: if content is unchanged, skip the commit and record “no new finalized GSC rows”; never trigger a deployment for a no-op.
  8. Retries: retry transient 429/5xx with exponential backoff and a small maximum attempt count; honor Retry-After; never loop indefinitely.
  9. Do not add a second Vercel Cron to duplicate the existing 05:30 automation.

18.4 Reusable multi-project config

Add a new authorized GSC property by adding a key/name to the site configuration, rather than copying API files:

const SITES = { /* team na 13 client projects nu mapping — naam public ma share karvana nahi */ };

The matching project key must also exist in data.json and in the health endpoint's expected project list. Keep these lists in sync; ideally move the project registry to one shared config module to prevent drift.

18.6 Trade-offs and safeguards

  • A shared multi-site dashboard reduces duplicate deployments, but all sites share a release cycle; test representative properties.
  • One large JSON is simple and minimizes GitHub operations. Partition by project/month only after measuring response size and performance.
  • Serverless instances may not share in-memory cache reliably. Never rely on memory cache for correctness.
  • Short caching can reduce repeat GitHub reads but may show briefly stale data. Keep current no-store behavior when freshness matters; add a measured short TTL only if acceptable.
  • Current API reads private GitHub main/data.json per request. The safest savings are reducing duplicate browser fetches, not removing authorization or hiding failures.

Reusable principle: one scheduler → one batch fetch → one merge → one commit → one health check; deploy only when code changes.
