2. What Vercel does

  • Hosts static HTML/CSS/JS.
  • Connects to GitHub and deploys on push.
  • Non-production branches get Preview deployments.
  • Configured production branch deploys to production.
  • api/*.js files become server-side Node.js Functions.
  • Environment Variables store secrets server-side.

Important: Current 05:30 GSC collection is done by existing scheduled automation, not Vercel Cron. A Vercel Cron hitting /api/gsc-health only checks data; it does not fetch GSC or update GitHub.

4. GitHub token → Vercel Environment Variable

The API reads private GitHub main/data.json, so Vercel needs a server-side GITHUB_TOKEN.

  1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens.
  2. Resource owner: client-a-store.
  3. Repository access: only gsc.
  4. Permissions: Contents Read-only; Metadata Read-only/default.
  5. Generate token; copy it only into Vercel. Never paste into chat, docs, source, HTML, screenshots, or logs.
  6. Vercel → project (vercel project) → Settings → Environment Variables.
  7. Name GITHUB_TOKEN; value = token; target = Preview (and branch restriction migration/vercel if using branch-specific preview env).
  8. Save and redeploy latest Preview deployment. Environment changes do not alter already-built deployments automatically.
  9. Test /api/gsc-health; expected ok:true, 13 expected/checked projects, allProjectsValid true.

Token must never be returned to browser. Rotate it if exposed or expired.

11. Vercel Cron – optional, not current data-fetch system

Vercel Cron sends an HTTP request to a deployed route. It does not magically connect GSC or write GitHub. If a cron calls /api/gsc-health, it only checks the snapshot. Full GSC ETL requires OAuth/service-account auth, API query code, merge/write logic, retries, idempotency/locking, and monitoring. Keep current working scheduler until replacement is tested end-to-end.

18.2 Deployment decision rule

  • Data-only change (new rows in data.json): do not redeploy Vercel. The API reads the latest GitHub main snapshot when requested.
  • Dashboard/API code change: push one reviewed commit to migration/vercel; Git integration creates one Preview deployment.
  • Preview passes and release approved: follow the production release process. Do not deploy for each daily data refresh.
  • More properties in same dashboard: add a site config entry; do not clone the entire dashboard/API for every site.
  • Different client/team with separate secrets, access rules, billing or branding: use a separate project/repo when isolation is needed.
  • Batch related code/config edits and deploy once; environment-variable changes also require a new deployment to take effect.

18.3 Keep GitHub, GSC and API usage low

  1. GSC: one Search Analytics query per property per daily run for the required date window; use only required dimensions (date) and metrics. Do not repeat identical queries in the same run.
  2. Backfill: query only missing/recent dates or a deliberate bounded lookback; merge by date key idempotently.
  3. GitHub: prepare the merged JSON in memory and commit once after all properties are processed; avoid one commit per site/date.
  4. Scheduler GitHub reads: read source once before merge and read back once after commit for validation.
  5. Dashboard: fetch only the selected site and selected date range; do not fetch all 13 sites on every page view unless portfolio totals require it.
  6. Health: run once after commit; no polling every few seconds.
  7. No-op: if content is unchanged, skip the commit and record “no new finalized GSC rows”; never trigger a deployment for a no-op.
  8. Retries: retry transient 429/5xx with exponential backoff and a small maximum attempt count; honor Retry-After; never loop indefinitely.
  9. Do not add a second Vercel Cron to duplicate the existing 05:30 automation.

18.4 Reusable multi-project config

Add a new authorized GSC property by adding a key/name to the site configuration, rather than copying API files:

const SITES = { /* mapping removed */ };

The matching project key must also exist in data.json and in the health endpoint's expected project list. Keep these lists in sync; ideally move the project registry to one shared config module to prevent drift.

18.6 Trade-offs and safeguards

  • A shared multi-site dashboard reduces duplicate deployments, but all sites share a release cycle; test representative properties.
  • One large JSON is simple and minimizes GitHub operations. Partition by project/month only after measuring response size and performance.
  • Serverless instances may not share in-memory cache reliably. Never rely on memory cache for correctness.
  • Short caching can reduce repeat GitHub reads but may show briefly stale data. Keep current no-store behavior when freshness matters; add a measured short TTL only if acceptable.
  • Current API reads private GitHub main/data.json per request. The safest savings are reducing duplicate browser fetches, not removing authorization or hiding failures.

Reusable principle: one scheduler → one batch fetch → one merge → one commit → one health check; deploy only when code changes.

  1. Client ne samjo        → shu vechay chhe, paisa kya thi aave chhe, brand naam shu chhe

  2. Data lo (3 period)     → GSC pages + queries (7 / 28 / 90 days, comparison sathe), GA4 Organic

Google already je page ne batave chhe (impressions) pan click nathi madta (low CTR / position 8–20), e pages ne pehla sudharo. Google je queries mate tamari site batave chhe pan matching page nathi, e mate navu page banavo.

PART J — Senior SEO ni jem vicharo (yaad rakhva jevu)

  • Impressions = Google no vishvas. Clicks = user no vishvas. Impressions chhe pan clicks nathi, etle snippet ke intent ni problem chhe.
  • Navi query = Google no hint. Google kahe chhe "aa topic mate tamne test karu chhu". Page ma eno jawab aapo.
  • Position 8–20 = sauthi saro ROI. Ochhi mehnat ma vadhu result male.
  • Blog traffic laave, collection paisa laave. Banne ne link thi jodo.
  • Pehla sudharo, pachhi navu banavo. Hal ni page ne rewrite karvu e navi page karta jaldi result aape.
  • Revenue 0 = pehla tracking check karo, SEO ne dosh na aapo.
  • Darek suggestion data thi. Data na hoy to suggestion na aapo, athva "hypothesis" lakho.
  • Measure karo: rewrite pachhi 2–4 week ma same page na CTR, position ane clicks sarkhavo, ane aavta report ma "Rewrite impact" section umero.

Numbers match rule + Security (badha reports mate)

  • Sheet, dashboard, live report, Looker — clicks/impressions/sessions GSC/GA4 mathi j aave (Semrush/Moz third-party estimates chhe). Client ne mokalta pehla 3–4 numbers cross-check karo; mismatch hoy to date range ane timezone pehla check karo.

## PART C — Data ne 6 sawal (aa j "mind" chhe)

Data aavya pachhi seedha report na banavo. Pehla aa 6 sawal pucho. Darek sawal no jawab report no ek section bane chhe.

### Sawal 1: "Overall site upar jay chhe ke niche?"
- Clicks, impressions, CTR ane position na totals current vs previous sarkhavo.
- **Client A 28d:** Clicks 743 → 843 (upar), Impr 68.5K → 65K (thoda niche), CTR 1.1% → 1.3% (upar).
- **Matlab:** impressions thodi ghati pan clicks vadhya. Etle je traffic aave chhe e vadhu relevant chhe. Aa **positive story** chhe.
- **Rule:** Clicks upar ane impr niche hoy to CTR sudharyo chhe. Clicks niche ane impr upar hoy to position ke snippet ni problem chhe.

### Sawal 2: "Kayu content kaam kare chhe?" (Blog vs other pages)
- URL ma `/blogs/` hoy e blog. Baki badhu collection, product, home.
- **Client A:** top impressions vala pages ma ghana blogs chhe (cutting-metal-with-a-skil-saw 5,711 impr, choose-the-right-blade 3,990). **Matlab:** blogs traffic laave chhe, pan revenue collections/products thi aave chhe. Etle **blog → collection internal link** sauthi mahatva nu kaam chhe.

### Sawal 3: "Shu badlayu?" (What changed section)

| Signal | Kevi rite shodhvu | Matlab shu |
|---|---|---|
| Clicks gainers | `clicks − prevClicks` sauthi vadhu | Kaam thayu chhe, client ne batavo |
| Impression gainers | `impr − prevImpr` sauthi vadhu | Google aa page ne navi queries mate test kare chhe. **Opportunity** |
| New keywords | prev impr = 0, current impr ≥ 5 | Google navo topic tamari site sathe jode chhe. **Nava content no idea** |
| Position movers | `prevPos − pos` vadhu | Ranking sudhri. Report ma batavo |
| Striking distance | position 8–20, impr ≥ 20 | Page 1 ni najik chhe. **Thodu kaam karo to vadhu clicks malse** |
| Low CTR | impr ≥ 100–300, CTR < 1% | Google batave chhe pan loko click nathi karta. **Title/meta/intent ni problem** |

### Sawal 4: "Loko shu search kare chhe?" (Keywords)
- **Branded** (Client A, Client A stone products): aa loko tamne already jane chhe. Aa SEO nu kaam nathi, brand nu chhe. **Alag tab ma rakho.**
- **Non-branded** (akemi, porcelain sink, tenax proseal): aa SEO nu saachu result chhe. **Main tab.**
- **Dhyan:** "akemi" ke "tenax" product brand chhe, store brand nathi. Etle e **non-branded** gane.

### Sawal 5: "SEO thi business ne shu malyu?" (GA4)
- Organic sessions, users, engagement, orders, revenue.
- **Client A:** 821 organic sessions pan **revenue $0, key events 0.** Sales nathi thata evu nathi, **tracking j nathi.**
- **Rule:** Revenue 0 hoy to pehla tracking check karo. Report ma "tracking not set up" lakho ane Fixes ma **High** priority aapo. Khota orders kyarey na mukvana.

### Sawal 6: "Shu karvu?" (Action, PART D) Upar na 5 sawal mathi je pages ane queries nikle, emathi **Rewrite / New content / Fix** nakki karo.

## PART D — Decision tree: Rewrite, New Page, ke Fix?

``` Query/page joyu │ ├─ Page chhe + impressions vadhu + CTR < 1% + position 4–20 │     └─► FULL PAGE REWRITE (title, meta, H1, body, FAQ — badhu navu) │ ├─ Page chhe + impressions vadhya pan position ghati │     └─► SEO-FOCUSED REWRITE (Google navi queries test kare chhe → e queries page ma umero) │ ├─ Page chhe + topic ni queries position 30+ par │     └─► SEO-FOCUSED REWRITE + collection ↔ blog internal links (topic "own" nathi thatu) │ ├─ Query ma impressions chhe pan MATCHING page j nathi │     ├─ Informational query (how, why, what, can, best, vs, guide)  ─► NEW BLOG POST │     └─ Commercial/product query (buy, sinks, blades, sealer, brand + product) ─► NEW COLLECTION │ ├─ Ek j intent ni 3+ queries, ane collection eni sathe match nathi kartu │     └─► NEW COLLECTION (athva hal ni collection ne split karo) │ └─ Page technical rite kharab (alt nathi, 2 H1, meta lambi, schema nathi, tracking nathi) └─► FIX (priority: High / Medium / Low) ```

### Search intent kevi rite olakhvo (simple rule)
| Query ma aa shabd | Intent | Page type |
|---|---|---|
| how, why, what is, can, tips, guide, vs, mistakes | Informational | Blog |
| best, top, review, compare | Commercial research | Blog (comparison) ke collection |
| product naam, brand + product, plural ("sinks", "blades"), price, buy | Transactional | Collection / Product |
| store naam | Navigational (branded) | Homepage |

### Priority kevi rite nakki karvi ``` Priority score ≈ Impressions × (position 4–20 hoy to vadhu) × Business value (product/collection > blog) ```
- Pehla e pages lo je **already page 1 ni najik** chhe ane **paisa vala** chhe (collections/products).
- Position 50+ vala pages par pehla kaam na karo. Ema vadhu mehnat lage ane result late aave.

4. Position 10 chhe, etle page 1 nu chhellu sthan. Thodu content sudhre to top 5 ma aavi shake.
